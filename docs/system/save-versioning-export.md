# [미구현] 세이브 호환·내보내기 설계

> 상태 기준: 2026-08-02
> 이전 제안 번호: 5
> 선행 구현: 로컬 저장소 기반 세션 스키마 v3, 자동 저장 1개, 수동 슬롯 8개

## 1. 목적

스토리와 런타임을 자주 개정해도 플레이어의 세이브를 잃지 않게 하고, 브라우저 저장소 밖으로 백업하고 복원할 수 있게 한다.

현재 세이브는 로컬 저장소에 저장되며 스키마 버전은 3이다. 저장과 불러오기는 구현되어 있지만 콘텐츠 빌드 식별, 파일 내보내기와 가져오기, 슬롯별 복구 백업은 없다.

## 2. 핵심 원칙

- 스키마 버전과 스토리 콘텐츠 버전을 별도로 관리한다.
- 마이그레이션 성공 전에는 원본 데이터를 덮어쓰지 않는다.
- 존재하지 않는 ID를 첫 캠페인이나 비슷한 장면으로 자동 대체하지 않는다.
- 저장은 검증을 통과한 완전한 객체 단위로 교체한다.
- 내보내기 파일에는 실행 가능한 코드와 비밀 정보를 넣지 않는다.
- 표시 언어 문자열 대신 안정 ID를 저장하고 현재 로케일에서 다시 해석한다.

## 3. 세이브 봉투 v4

각 프로필과 세션은 공통 봉투 안에 저장한다.

    schema_version
    game_version
    content_fingerprint
    record_type
    record_id
    created_at
    saved_at
    payload

세션 payload는 게임 모드 설계에 따라 다음 값을 반드시 포함한다.

    game_mode_id
    campaign_id
    continuity_id
    view_layer
    layer_policy
    current_event_id
    current_scene_id
    current_node_id

content_fingerprint는 빌드 런타임의 source_sha256을 사용한다. game_version은 배포 애플리케이션 버전이며, schema_version은 데이터 구조의 마이그레이션 기준이다.

## 4. 저장소 추상화

플레이어는 구체적인 localStorage 호출 대신 PlayerStorage 인터페이스에 의존한다.

    readProfile
    writeProfile
    listSlots
    readSlot
    writeSlot
    deleteSlot
    exportAll
    importArchive

첫 구현은 기존 localStorage 어댑터를 유지한다. 용량이나 썸네일 요구가 커지면 같은 인터페이스 아래 IndexedDB 어댑터를 추가할 수 있다.

키 이름에는 환경, 스키마 계열, 레코드 종류와 슬롯 ID를 포함한다. 슬롯 번호만으로 프로필과 세션을 구분하지 않는다.

## 5. 원자적 저장과 복구

슬롯을 저장할 때 다음 순서를 사용한다.

1. 새 데이터를 메모리에서 직렬화하고 스키마를 검증한다.
2. 임시 키에 기록한다.
3. 임시 키를 다시 읽어 체크섬과 필수 필드를 확인한다.
4. 기존 슬롯을 해당 슬롯의 backup 키로 복사한다.
5. 검증된 임시 데이터를 본 키에 기록한다.
6. 본 키를 다시 검증한 뒤 임시 키를 제거한다.

중간 단계에서 실패하면 본 키를 유지하고 오류를 알린다. 불러오기 시 본 슬롯이 손상됐고 backup이 유효하면 플레이어에게 복구 여부를 묻는다.

자동 저장도 같은 절차를 쓰며, 수동 슬롯의 백업을 재사용하지 않는다.

## 6. 마이그레이션

마이그레이션은 순차적인 순수 함수 레지스트리로 관리한다.

    v1 to v2
    v2 to v3
    v3 to v4

각 함수는 입력을 변경하지 않고 새 객체를 반환한다. 중간 버전도 매 단계 스키마 검증을 통과해야 한다.

v3에서 v4로 올릴 때는 다음을 수행한다.

- 기존 mode와 campaignId를 game_mode_id와 campaign_id로 변환한다.
- 캠페인 레지스트리에서 continuity_id와 layer_policy를 해석한다.
- 현재 런타임 source_sha256을 무조건 덮어쓰지 않고 legacy 출처를 표시한다.
- 변환할 수 없는 캠페인은 원본을 보존하고 복구 불가 사유를 기록한다.

마이그레이션 성공 후에도 최초 원본은 한 세대의 backup으로 남긴다.

## 7. 콘텐츠 호환성 판정

### 동일 fingerprint

스키마 검증 후 바로 불러온다.

### 다른 fingerprint

다음 안정 ID를 현재 런타임과 대조한다.

- 모드, 캠페인, 연속성과 경로
- 현재 이벤트, 장면과 노드
- 완료한 이벤트와 선택지
- 상태 스키마 키
- 선택된 대사 variant

ID가 바뀐 경우 story migration registry에 명시적인 alias가 있을 때만 변환한다. alias는 이전 ID, 새 ID, 적용 가능한 fingerprint 범위를 가진다.

현재 노드만 사라졌고 현재 이벤트의 안전한 재진입점이 선언되어 있으면 그 지점으로 복구할 수 있다. 안전한 재진입점도 없으면 불러오기를 중지하고 세이브 내보내기를 제공한다.

### 더 새로운 스키마

현재 게임이 이해할 수 없는 새 schema_version은 읽기 전용 미리보기만 표시하고 덮어쓰지 않는다.

## 8. 내보내기 형식

내보내기 파일은 UTF-8 JSON 한 개로 만든다.

    format: love-office-save
    format_version
    exported_at
    game_version
    profile
    autosave
    slots
    legacy_records
    checksum

파일 이름에는 게임 이름과 날짜만 사용하고 플레이어 이름이나 경로 같은 민감할 수 있는 정보를 넣지 않는다.

체크섬은 우발적인 손상을 찾기 위한 것이며 보안 서명이나 부정행위 방지 수단으로 설명하지 않는다.

## 9. 가져오기 흐름

1. 파일 크기와 JSON 형식을 검사한다.
2. format과 format_version을 확인한다.
3. 위험한 객체 키와 알 수 없는 실행형 데이터를 거부한다.
4. 모든 레코드를 메모리에서 마이그레이션하고 호환성 판정을 수행한다.
5. 적용 전에 가져올 프로필, 자동 저장, 슬롯과 충돌 목록을 미리 보여 준다.
6. 플레이어가 merge 또는 replace를 선택한다.
7. 현재 전체 데이터를 자동 백업 파일로 만든 뒤 적용한다.
8. 적용된 각 레코드를 다시 읽어 검증한다.

### 충돌 규칙

- 같은 ending_id는 최초 달성일의 이른 값, 최근 달성일의 늦은 값과 큰 clear_count를 보존한다.
- 해금 목록은 합집합으로 병합한다.
- 같은 슬롯 ID의 세션은 자동 병합하지 않고 기존 유지, 가져온 데이터로 교체 또는 빈 슬롯에 복사 중 하나를 고른다.
- 자동 저장은 명시적인 교체 승인 없이는 덮어쓰지 않는다.
- 서로 다른 continuity의 상태는 병합하지 않는다.

## 10. 보안과 제한

- 허용 최대 파일 크기와 레코드 수를 둔다.
- __proto__, prototype, constructor 같은 위험 키를 거부한다.
- HTML, JavaScript, 파일 경로와 외부 URL을 실행하거나 자동으로 열지 않는다.
- 토큰, 계정 정보, 로컬 절대 경로와 디버그 로그를 내보내지 않는다.
- 오류 메시지는 데이터 일부를 화면이나 로그에 그대로 출력하지 않는다.
- 가져오기 실패 파일은 저장소에 자동 보관하지 않는다.

## 11. UI

- 저장 화면에 전체 백업 내보내기와 백업 가져오기를 제공한다.
- 각 슬롯은 저장 시각, 모드, 캠페인, 현재 장면의 안전한 표시 이름과 호환 상태를 보여 준다.
- 호환 상태는 정상, 변환 필요, 복구 가능, 현재 버전에서 불러올 수 없음으로 구분한다.
- 가져오기 미리보기에서 변경될 항목과 유지될 항목을 분리해 보여 준다.
- 손상이나 비호환 세이브에도 삭제보다 내보내기를 먼저 제공한다.

## 12. 검증 계약

자동 테스트는 다음을 확인한다.

- 모든 이전 스키마 fixture가 v4로 결정적으로 변환되는가
- 마이그레이션 실패 시 원본 문자열이 바뀌지 않는가
- 저장 도중 각 단계가 실패해도 마지막 유효 슬롯을 읽을 수 있는가
- 다른 fingerprint에서 사라진 ID를 조용히 대체하지 않는가
- export 후 빈 저장소에 import하면 동일한 논리 데이터가 복원되는가
- merge가 다른 continuity의 상태를 합치지 않는가
- 과대 파일, 위험 키, 잘못된 체크섬과 새 버전 파일을 안전하게 거부하는가

## 13. 구현 순서

1. v4 봉투 스키마와 PlayerStorage 인터페이스 추가
2. localStorage 어댑터와 원자적 저장·backup 구현
3. v1부터 v4까지 fixture 기반 마이그레이션 테스트 고정
4. source_sha256 기반 콘텐츠 호환성 검사 추가
5. 내보내기, 가져오기와 충돌 미리보기 구현
6. story migration registry와 안전 재진입점 validator 추가

## 14. 인수 조건

- 브라우저 저장소가 비어 있어도 백업 파일 하나로 프로필과 모든 슬롯을 복원할 수 있다.
- 저장 중 실패를 주입해도 이전 유효 슬롯이 남는다.
- 현재 콘텐츠와 맞지 않는 세이브가 잘못된 장면으로 자동 진입하지 않는다.
- 더 새로운 버전 파일을 가져와도 현재 데이터가 변경되지 않는다.
- 가져오기 교체 전에 현재 데이터 백업이 자동으로 생성된다.
- 내보내기 파일에 번역된 대사, 비밀 정보와 로컬 절대 경로가 없다.

## 15. 제외 범위

- 계정 로그인과 클라우드 동기화
- 세이브 암호화, DRM과 부정행위 방지
- 서버 데이터베이스와 원격 백업 보관
- 운영체제별 네이티브 파일 선택기의 세부 구현
